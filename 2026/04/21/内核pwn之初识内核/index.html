内核pwn之初识内核

过渡

还记得我们在用户态 pwn 中，最终的目标是劫持程序的控制流，执行 system("/bin/sh") 来获得一个 shell。这个 shell 的权限通常和运行该程序的用户一样。

但在内核 pwn 中，情况不同了。我们的目标是利用内核或内核模块中的漏洞，将我们普通用户的权限提升为 root 权限。这通常被称为本地权限提升 (Local Privilege Escalation, LPE)简称提权

前置知识

在学习内核pwn之前先来看看内核相关概念

操作系统内核

简介:

操作系统内核（Operation System Kernel）本质上也是一种软件，可以看作是普通应用程式与硬件之间的一层中间层，其主要作用便是调度系统资源、控制 IO 设备、操作网络与文件系统等，并为上层应用提供便捷、抽象的应用接口。

既然操作系统内核本质上是软件，且绝大多数是用 C 语言和少量汇编写的，那么所有在用户态（User-space）存在的漏洞，在内核态（Kernel-space）都可能存在！

操作系统内核与用户进程本质上并无差异，都为代码+数据，不同之处在于当CPU执行不同进程代码时的权限不同，内核态运行代码是高权限，有着完全的硬件访问能力，用户态运行代码是低权限，只有部分硬件访问能力。

这两种不同的状态是基于硬件来实现的

Rings

分级保护域hierarchical protection domains，别名保护环，简称为Rings。

简单来讲分级保护域是由 CPU 硬件（芯片）直接提供的一种安全机制。CPU 将系统的运行状态划分成不同的特权级别。级别越高的代码，能执行的指令越多，能访问的内存范围越大。

在经典的 Intel x86 架构中，硬件提供了 4 个特权级别：Ring 0, Ring 1, Ring 2, Ring 3。数字越小，权限越高。

一般来说我们只会使用Ring0 和 Ring3 对应操作系统内核和用户进程

用户态和内核态的区别简单讲：

  • 用户态：CPU 运行在 ring3 + 用户进程运行环境上下文。
  • 内核态：CPU 运行在 ring0 + 内核代码运行环境上下文。

状态切换

CPU进行状态切换一般就是这几个方法：

  1. 特权级相关指令：当 CPU 运行这些指令时会发生运行状态的改变，例如 iret 指令（ring0->ring3）或是 sysenter 指令（ring3->ring0）。

    注意：

    ring3->ring0 并不是只能通过系统调用来切换比如以下的硬件中断和异常

  2. 硬件中断（Hardware Interrupts）：网卡收到数据了、键盘被按下了，硬件发信号给 CPU，CPU 暂停当前 Ring 3 的工作，切到 Ring 0 去处理。

  3. 异常（Exceptions）：比如 Ring 3 程序触发了缺页异常（Page Fault），CPU 自动切入 Ring 0 去分配内存。

思考：

通过了解状态切换，可以知道一些内核pwn中的套路就是利用ioctl()函数(一个基于syscall的函数)带着payload进入 ring0 内核态，然后在内核态中触发漏洞提权，最后利用特权级指令返回 ring3 用户态

user space to kernel space （系统调用）

系统调用是内核和用户通信的直接接口。

我们主要关注比较常用的系统调用即可

具体过程：当系统调用指令执行后，CPU便进入内核态，然后在内核态下完成一系列操作

1.换上内核的“工作服”:

  • 第一步执行swapgs指令，这一步是雷打不动的，通过 swapgs 切换 GS 段寄存器，将 GS 寄存器值和一个特定位置(MSR_KERNEL_GS_BASE)的值进行交换，目的是保存 GS 值，同时将该位置的值作为内核执行时的 GS 值使用。（这里浅浅说一下这个GS与多核隔离有关）

2.安检阶段：

  • 判断 x32_abi：
    • 内核代码会检查 rax 系统调用号的第 30 位。如果是 x32，内核会跳转到另一套处理逻辑（使用 32 位的指针转换规则）。
  • 边界检查：
    • 将 rax 与 NR_syscalls（系统支持的最大系统调用号）进行比较，防止恶意调用号导致 sys_call_table 越界读取。
  • 查找 sys_call_table：
    • 一旦校验通过，内核会计算 sys_call_table + rax * 8 的地址。
    • 执行 call（或通过 Retpoline 机制跳转），跳进该地址指向的内核 C 函数（如 sys_read）。

3.参数校验与数据拷贝：

  • 地址空间检查：内核必须检查你传进来的 buf 内存地址是不是真的在 Ring 3 的范围内。如果这个指针指向内核空间，内核必须拒绝访问。
  • copy_from_user：因为内核开启了 SMAP 保护（不能直接读 Ring 3 内存），内核必须调用这个专门的函数，把你 buf 里的 100 字节数据，安全地拷贝到内核态的一块内存中，然后再去处理。

5.结果回传：

copy_to_user：内核再次调用这个安全函数，把内核里准备好的数据，拷贝回你当时提供的用户态内存里。

如果内核没有正确清空它的临时缓冲区，就把数据 copy_to_user 给了你，就会导致内核信息泄露（Info Leak）！我们就能在用户态拿到属于内核的堆地址或代码地址，从而绕过 KASLR（内核地址随机化）

kernel space to user space

退出时，流程如下：

  1. 通过 swapgs 恢复 GS 值。
  2. 通过 sysretq(它只能回到 rcx 寄存器指定的地址，并将 r11 恢复为 rflags。它不从栈上弹数据) 或者 iretq 恢复到用户控件继续执行。如果使用 iretq 还需要给出用户空间的一些信息（CS, eflags/rflags, esp/rsp 等）。

在攻击中开启了KPTI(内核页表隔离)的话，还需要一些额外的步骤

进程权限管理

进程描述符

在linux内核中，进程和线程都被统一抽象为”任务”，由结构体task_struct完整描述。它包含了内核管理进程所需的一切信息：内存空间、打开的文件、信号、寄存器状态以及权限凭证

这里，我们可以重点关注以下几点：

  • 进程标识符 (pid/tgid)：pid是内核级线程ID，而我们常说的进程ID其实是tgid（线程组ID）。在单线程程序中，两者数值相等。
  • 进程名 (comm)：一个16字节的字符数组，保存了进程的名字。它在利用中常被用作“锚点”，帮助我们定位到进程描述符在内存中的地址。
  • 权限指针 (real_cred & cred)：这是内核pwn利用中的关键。它们是两个指向cred结构体的指针。

cred

Linux的权限管理并不是简单的“Root与非Root”，而是细粒度的权限控制机制。这些信息存储在 struct cred 中。

一个 cred 结构体中记载了一个进程四种不同的用户 ID，在通常情况下这几个 ID 应当都是相同的：

  • 真实用户 ID（real UID）：标识一个进程启动时的用户 ID
  • 保存用户 ID（saved UID）：标识一个进程最初的有效用户 ID
  • 有效用户 ID（effective UID）：标识一个进程正在运行时所属的用户 ID，一个进程在运行途中是可以改变自己所属用户的，因而权限机制也是通过有效用户 ID 进行认证的，内核通过 euid 来进行特权判断；为了防止用户一直使用高权限，当任务完成之后，euid 会与 suid 进行交换，恢复进程的有效权限
  • 文件系统用户 ID（UID for VFS ops）：标识一个进程创建文件时进行标识的用户 ID

用户组ID与用户ID类似。

UID 与 EUID

  • UID：真实的用户ID。比如你以普通用户运行 su，此时 UID 仍然是普通用户。
  • EUID：有效用户ID。内核进行权限判定时，主要看 EUID！ su 命令设置了 Set-UID 位，执行时 EUID 会变成 root (0)。所以内核认为它有 root 权限。

提权的本质：将当前进程的 cred 结构体中的 uid, gid, euid, egid, fsuid, fsgid 全部修改为 0。

Capabilities (能力机制)

现代 Linux 内核不再盲目信任 UID=0，而是将 Root 权限拆分成了几十种具体的 Capabilities（如 CAP_SYS_ADMIN, CAP_NET_RAW 等）。

  • 即使 UID=0，如果没有对应的 Capability，依然无法执行特定的内核操作。
  • cap_effective 是一个位图，标识当前进程当前生效的能力。
  • 在内核 Pwn 中，最完美的提权不仅是将 UID 置 0，还需要将 cap_effective 置为全 1（即 0xFFFFFFFFFFFFFFFF），这通常通过赋值 init_cred 或调用专用内核函数来实现。

cred 与 real_cred

  • real_cred：客观凭证，代表“我真正是谁”。通常在进程启动时设置，一般不参与直接的权限判定，而是用于信号传递等场景。
  • cred：主观凭证，代表“我目前以什么身份行事”。内核进行权限检查（如 capable(), ns_capable()）时，检查的都是 cred。
  • Pwn 注意事项：在进行内存覆写提权时，最安全的做法是将 cred 和 real_cred 同时改掉，否则某些安全检查可能会发现身份不一致而报错。

进程权限改变

前面我们讲到，一个进程的权限是由位于内核空间的 cred 结构体进行管理的，那么我们不难想到：只要改变一个进程的 cred 结构体，就能改变其执行权限。

Loadable Kernel Module（可加载内核模块）->LKMS

LKM是什么？

  • 本质：编译为.ko文件的内核态代码，可以在运行时动态插入/卸载，无需重新编译或者重启内核。

  • 常见用途：设备驱动、文件系统、网络协议栈、安全模块

LKMs 的文件格式和用户态的可执行程序相同，Linux 下为 ELF，Windows 下为 exe/dll，mac 下为 MACH-O，因此我们可以用 IDA 等工具来分析内核模块。

模块可以被单独编译，但不能单独运行。它在运行时被链接到内核作为内核的一部分在内核空间运行，这与运行在用户控件的进程不同。

模块通常用来实现一种文件系统、一个驱动程序或者其他内核上层的功能。

内核交互

用户态想与内核进行交互一般是用系统调用

系统调用

系统调用，指的是用户空间的程序向操作系统内核请求需要更高权限的服务，比如 IO 操作或者进程间通信。系统调用提供用户程序与操作系统间的接口，部分库函数（如 scanf，puts 等 IO 相关的函数实际上是对系统调用的封装（read 和 write））。

ioctl

在 *NIX 中一切都可以被视为文件，因而一切都可以以访问文件的方式进行操作，为了方便，Linux 定义了系统调用 ioctl 供进程与设备之间进行通信。

函数原型:

  • fd (File Descriptor)：文件描述符。告诉内核你要跟哪个设备对话（比如你刚才 open(“/dev/vuln”) 得到的返回值）。
  • request (也就是 CMD)：控制命令码。告诉设备你想干什么（比如 1 代表开灯，2 代表关灯）。
  • … (也就是 Arg)：Payload 的载体！ 这是一个没有任何类型限制的参数。你可以传一个整数，也可以传一个指向极其复杂的嵌套结构体的指针。

使用 ioctl 进行通信的原因：

操作系统提供了内核访问标准外部设备的系统调用，因为大多数硬件设备只能够在内核空间内直接寻址, 但是当访问非标准硬件设备这些系统调用显得不合适, 有时候用户模式可能需要直接访问设备。

比如，一个系统管理员可能要修改网卡的配置。现代操作系统提供了各种各样设备的支持，有一些设备可能没有被内核设计者考虑到，如此一来提供一个这样的系统调用来使用设备就变得不可能了。

为了解决这个问题，内核被设计成可扩展的，可以加入一个称为设备驱动的模块，驱动的代码允许在内核空间运行而且可以对设备直接寻址。一个 Ioctl 接口是一个独立的系统调用，通过它用户空间可以跟设备驱动沟通。对设备驱动的请求是一个以设备和请求号码为参数的 Ioctl 调用，如此内核就允许用户空间访问设备驱动进而访问设备而不需要了解具体的设备细节，同时也不需要一大堆针对不同设备的系统调用。

常见内核态函数

printk：用于在内核空间中打印调试信息或状态信息，通过dmesg查看调试信息。

copy_from_user()：用户空间的数据拷贝到内核空间。

copy_to_user()：内核空间的数据拷贝到用户空间。

kmalloc()，内核态的内存分配函数，和 malloc() 相似，但使用的是 slab/slub 分配器。

kfree()，同 kmalloc。

此外，kernel 管理进程，因此 kernel 也记录了进程的权限。kernel 中有两个可以方便的改变权限的函数：

  • int commit_creds(struct cred *new)
  • struct cred* prepare_kernel_cred(struct task_struct* daemon)

从函数名也可以看出，执行 commit_creds(prepare_kernel_cred(&init_task)) 即可获得 root 权限，即拷贝 init 进程的 cred 作为当前进程的新的 credentials。

执行 commit_creds(prepare_kernel_cred(&init_task)) 也是最常用的提权手段，这些函数与变量的地址都可以在 /proc/kallsyms 中查看（较老的内核版本中是 /proc/ksyms），该文件的内容通常需要 root 权限才能正确查看。

内核pwn中相关文件

  • run.sh/start.sh：一个用于启动kernel的shell脚本，多使用qemu，保护措施与qemu不同的启动参数有关，因此我们可以通过阅读该脚本来了解题目所开保护

  • bzImage：压缩的内核二进制文件，可以通过extract-vmlinux bzImage > vmlinux这个命令来提取出vmlinux

  • vmlinux ：解压后的未压缩 ELF 内核镜像，可用来调试内核模块和获取gadget

  • rootfs.cpio: 文件系统映像
